# 🗄️ PostgreSQL Connection Pool

## Что такое Connection Pool?

Connection Pool — это набор заранее созданных подключений к БД, которые переиспользуются между запросами.

### Зачем это нужно?

❌ **Без Pool:**
```
Запрос 1 → Открыть соединение (200ms) → Запрос → Закрыть соединение
Запрос 2 → Открыть соединение (200ms) → Запрос → Закрыть соединение
Запрос 3 → Открыть соединение (200ms) → Запрос → Закрыть соединение
```

✅ **С Pool:**
```
Pool: [conn1, conn2, conn3, ...] ← переиспользуются
Запрос 1 → Взять conn1 → Запрос (10ms) → Вернуть conn1
Запрос 2 → Взять conn2 → Запрос (10ms) → Вернуть conn2
Запрос 3 → Взять conn1 → Запрос (10ms) → Вернуть conn1
```

**Выигрыш:** 200ms → 10ms (в 20 раз быстрее!)

---

## 📊 Конфигурация Pool

### Основные параметры

| Параметр | Default | Описание | Рекомендация |
|----------|---------|----------|--------------|
| `DB_POOL_MAX` | 10 | Максимум соединений в pool | Development: 10, Production: 20-50 |
| `DB_POOL_MIN` | 2 | Минимум соединений (всегда активных) | 2-5 |
| `DB_CONNECTION_TIMEOUT` | 30000ms | Таймаут ожидания соединения | 30000 (30 сек) |
| `DB_IDLE_TIMEOUT` | 30000ms | Простой перед закрытием | 30000 (30 сек) |
| `DB_MAX_LIFETIME` | 1800s | Макс. время жизни соединения | 1800 (30 минут) |
| `DB_QUERY_TIMEOUT` | 10000ms | Таймаут выполнения запроса | 10000 (10 сек) |
| `DB_STATEMENT_TIMEOUT` | 15000ms | PostgreSQL statement timeout | 15000 (15 сек) |

---

## ⚙️ Детальное описание параметров

### 1. **DB_POOL_MAX** — Максимум соединений

**Что это:**
Максимальное количество одновременных соединений к БД.

**Как выбрать:**
```
Формула: DB_POOL_MAX = (CPUs * 2) + Effective Spindle Count

Для типичного сервера:
- 4 CPU cores → 10-20 соединений
- 8 CPU cores → 20-40 соединений

ВАЖНО: PostgreSQL имеет лимит max_connections (обычно 100-200)
```

**Development:** `10`
**Production:** `20-50` (зависит от нагрузки)

**Слишком много:**
- ❌ Лишняя память на сервере БД
- ❌ Замедление PostgreSQL (context switching)

**Слишком мало:**
- ❌ Запросы будут ждать свободное соединение
- ❌ Возможны таймауты при высокой нагрузке

---

### 2. **DB_POOL_MIN** — Минимум соединений

**Что это:**
Количество соединений, которые всегда остаются открытыми.

**Как работает:**
```
Pool запускается → Создаёт DB_POOL_MIN соединений
Приходит нагрузка → Создаются новые до DB_POOL_MAX
Нагрузка спала → Закрываются до DB_POOL_MIN
```

**Рекомендация:** `2-5`

**Зачем:**
- ✅ Быстрый старт (соединения уже открыты)
- ✅ Не нужно ждать подключения при первом запросе

---

### 3. **DB_CONNECTION_TIMEOUT** — Таймаут ожидания соединения

**Что это:**
Сколько ждать свободное соединение из pool, прежде чем выдать ошибку.

**Когда срабатывает:**
```
Все 10 соединений заняты →
Новый запрос ждёт свободное →
Через 30 секунд → TimeoutError
```

**Рекомендация:** `30000ms` (30 секунд)

**Типичные ошибки:**
```
Error: timeout exceeded when trying to connect
```

**Решение:**
- Увеличить `DB_POOL_MAX`
- Оптимизировать медленные запросы
- Проверить, нет ли утечек соединений

---

### 4. **DB_IDLE_TIMEOUT** — Простой соединения

**Что это:**
Через сколько закрыть неиспользуемое соединение.

**Как работает:**
```
Соединение использовано → Возвращено в pool
30 секунд простоя → Закрыто (если > DB_POOL_MIN)
```

**Рекомендация:** `30000ms` (30 секунд)

**Зачем:**
- ✅ Экономия ресурсов БД в периоды низкой нагрузки
- ✅ Автоматическое масштабирование pool

---

### 5. **DB_MAX_LIFETIME** — Максимальное время жизни

**Что это:**
Максимальное время существования одного соединения.

**Зачем:**
- ✅ Предотвращает проблемы с "зависшими" соединениями
- ✅ Автоматическая ротация соединений
- ✅ Обновление конфигурации PostgreSQL без рестарта

**Рекомендация:** `1800s` (30 минут)

**Как работает:**
```
Соединение создано → Живёт 30 минут →
Автоматически закрывается → Создаётся новое
```

---

### 6. **DB_QUERY_TIMEOUT** — Таймаут запроса

**Что это:**
Максимальное время выполнения одного запроса.

**Рекомендация:** `10000ms` (10 секунд)

**Когда срабатывает:**
```sql
-- Медленный запрос
SELECT * FROM notes WHERE content LIKE '%text%';
-- Работает дольше 10 секунд →
-- Error: Query read timeout
```

**Защищает от:**
- ❌ Медленных запросов без индексов
- ❌ Блокировок (deadlocks)
- ❌ Зависших транзакций

---

### 7. **DB_STATEMENT_TIMEOUT** — PostgreSQL timeout

**Что это:**
Таймаут на уровне PostgreSQL (более строгий).

**Рекомендация:** `15000ms` (15 секунд)

**Разница с DB_QUERY_TIMEOUT:**
```
DB_QUERY_TIMEOUT (10s)     ← Node.js таймаут
    ↓
DB_STATEMENT_TIMEOUT (15s) ← PostgreSQL таймаут (резервный)
```

**Зачем два:**
- Node.js таймаут срабатывает первым (10s)
- PostgreSQL таймаут — подстраховка (15s)

## 🎯 Рекомендуемые конфигурации

### Development (локальная разработка)

```env
DB_POOL_MAX=10
DB_POOL_MIN=2
DB_CONNECTION_TIMEOUT=30000
DB_IDLE_TIMEOUT=30000
DB_MAX_LIFETIME=1800
DB_QUERY_TIMEOUT=10000
DB_STATEMENT_TIMEOUT=15000
```

### Production (малая нагрузка, 1-100 RPS)

```env
DB_POOL_MAX=20
DB_POOL_MIN=5
DB_CONNECTION_TIMEOUT=30000
DB_IDLE_TIMEOUT=60000
DB_MAX_LIFETIME=3600
DB_QUERY_TIMEOUT=10000
DB_STATEMENT_TIMEOUT=15000
```

### Production (средняя нагрузка, 100-1000 RPS)

```env
DB_POOL_MAX=50
DB_POOL_MIN=10
DB_CONNECTION_TIMEOUT=30000
DB_IDLE_TIMEOUT=60000
DB_MAX_LIFETIME=3600
DB_QUERY_TIMEOUT=5000
DB_STATEMENT_TIMEOUT=10000
```

### Production (высокая нагрузка, 1000+ RPS)

```env
DB_POOL_MAX=100
DB_POOL_MIN=20
DB_CONNECTION_TIMEOUT=10000
DB_IDLE_TIMEOUT=30000
DB_MAX_LIFETIME=1800
DB_QUERY_TIMEOUT=3000
DB_STATEMENT_TIMEOUT=5000
```

## 📈 Мониторинг Pool

### События логируются автоматически

В логах вы увидите:
```json
{
  "level": "info",
  "msg": "Creating PostgreSQL pool",
  "max": 10,
  "min": 2,
  "connectionTimeout": 30000,
  "idleTimeout": 30000,
  "queryTimeout": 10000
}

// При каждом подключении (уровень debug)
{ "level": "debug", "msg": "New PostgreSQL client connected" }
{ "level": "debug", "msg": "PostgreSQL client acquired from pool" }
{ "level": "debug", "msg": "PostgreSQL client removed from pool" }

// Ошибки
{ "level": "error", "msg": "Unexpected error on idle PostgreSQL client" }
```

### Метрики для мониторинга

Добавьте в будущем:
- Количество активных соединений
- Количество ожидающих запросов
- Среднее время ожидания соединения
- Количество таймаутов

## 🐛 Типичные проблемы

### Problem 1: "timeout exceeded when trying to connect"

**Причина:** Все соединения заняты.

**Решение:**
```env
# Увеличить максимум
DB_POOL_MAX=20  # было 10
```

### Problem 2: "Query read timeout"

**Причина:** Запрос работает дольше `DB_QUERY_TIMEOUT`.

**Решение:**
1. Оптимизировать запрос (добавить индексы)
2. Увеличить таймаут для специфических запросов
3. Разбить сложный запрос на несколько

### Problem 3: Высокая нагрузка на PostgreSQL

**Причина:** Слишком много соединений.

**Решение:**
```env
# Уменьшить максимум
DB_POOL_MAX=10  # было 50

# Увеличить время простоя
DB_IDLE_TIMEOUT=60000  # 1 минута
```

### Problem 4: Медленный первый запрос

**Причина:** `DB_POOL_MIN=0`, соединения создаются по требованию.

**Решение:**
```env
# Создавать соединения при старте
DB_POOL_MIN=5
```

## 💡 Best Practices

1. **Не закрывайте соединения вручную** — pool управляет ими
2. **Всегда используйте `client.release()`** или `try/finally`
3. **Мониторьте метрики pool** — активные/ожидающие соединения
4. **Настройте PostgreSQL `max_connections`** — должно быть больше суммы всех pool
5. **Используйте транзакции с `client.query()`** — не блокируйте pool
6. **Тестируйте под нагрузкой** — используйте `k6`, `autocannon` для нагрузочного тестирования
